## 1. REPOSITORY (Репозиторий)

### Что делает этот паттерн

**Repository** создаёт слой абстракции между бизнес-логикой и базой данных. Вместо того чтобы писать SQL-запросы напрямую в коде сервиса, вы обращаетесь к объекту-репозиторию, который предоставляет методы вроде `getById()`, `save()`, `delete()`.

```python
# Без Repository (плохо)
def get_test(test_id):
    result = db.execute("SELECT * FROM tests WHERE id = ?", test_id)
    return Test(**result)

# С Repository (хорошо)
class TestRepository:
    def get_by_id(self, test_id: int) -> Test:
        ...

test = test_repo.get_by_id(test_id)
```

### Где применяется в SkillFlow

| Сущность | Репозиторий | Методы |
|----------|-------------|--------|
| `User` | `UserRepository` | `get_by_email()`, `get_by_telegram_id()`, `save()` |
| `Test` | `TestRepository` | `get_published()`, `get_by_author()`, `save()` |
| `TestAttempt` | `AttemptRepository` | `get_by_student()`, `get_best_attempt()`, `save()` |
| `Rating` | `RatingRepository` | `get_leaderboard()`, `update_score()`, `get_position()` |

### Почему именно этот паттерн

| Критерий | Объяснение |
|----------|------------|
| **Тестируемость** | Можно заменить реальную БД на mock-объект и тестировать логику без подключения к PostgreSQL |
| **Изоляция изменений** | Если решите сменить БД (PostgreSQL → MySQL), меняете только репозиторий, а не весь код |
| **Единый доступ** | Все запросы к сущности в одном месте, легче искать и оптимизировать |
| **Чистая логика** | Сервисы не содержат SQL, только бизнес-правила |

### Почему не альтернативы

| Альтернатива | Почему отказались |
|--------------|-------------------|
| **Active Record** (модель сама себя сохраняет) | Смешивает логику сущности с доступом к БД, сложно тестировать |
| **Прямые SQL-запросы в контроллерах** | Код становится нечитаемым, невозможно переиспользовать, высокий риск SQL-инъекций |
| **ORM без абстракции** | SQLAlchemy хорош, но без Repository слой всё равно «протекает» в сервисы |

### Вердикт

**Используем**, потому что это стандарт индустрии для приложений с базой данных. Без него код быстро превратится в «лапшу» с SQL-запросами по всему проекту.

## 2. STATE MACHINE (Машина Состояний)

### Что делает этот паттерн

**State Machine** явно описывает все возможные состояния объекта и допустимые переходы между ними. Объект не может перейти в некорректное состояние — машина состояний это заблокирует на уровне кода.

```python
# Без State Machine (плохо)
test.status = "PUBLISHED"  # А если тест не прошёл модерацию?

# С State Machine (хорошо)
test.state_machine.transition_to("PUBLISHED")  # Выбросит ошибку, если переход недопустим
```

### Где применяется в SkillFlow

**Сущность `Test`** имеет жизненный цикл:

```
┌─────────────────────────────────────────────────────────────────┐
│                    ЖИЗНЕННЫЙ ЦИКЛ ТЕСТА                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  DRAFT ──[отправить]──> PENDING_MODERATION                     │
│    │                        │                                  │
│    │                        ├──[одобрить]──> PUBLISHED         │
│    │                        │                                  │
│    │                        └──[отклонить]──> DRAFT            │
│    │                                                           │
│    └──[удалить]──> ARCHIVED                                    │
│                                                                 │
│  PUBLISHED ──[архивировать]──> ARCHIVED                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Недопустимые переходы (блокируются):**
- `DRAFT` → `PUBLISHED` (нельзя опубликовать без модерации)
- `ARCHIVED` → `PUBLISHED` (нельзя опубликовать архивный тест)
- `PUBLISHED` → `DRAFT` (нельзя вернуть опубликованный тест в черновики)

### Почему именно этот паттерн

| Критерий | Объяснение |
|----------|------------|
| **Защита от ошибок** | Невозможно случайно перевести тест в некорректный статус |
| **Явная логика** | Все переходы описаны в одном месте, легко понять и изменить |
| **Валидация на уровне кода** | Ошибка обнаруживается до записи в БД |
| **Аудит** | Легко логировать все переходы состояний |

### Почему не альтернативы

| Альтернатива | Почему отказались |
|--------------|-------------------|
| **Просто поле `status` в БД** | Ничего не мешает поставить некорректное значение, валидация только в UI |
| **if-else в каждом методе** | Код дублируется, легко пропустить проверку в новом месте |
| **Триггеры в БД** | Логика состояний «спрятана» в БД, сложно тестировать и документировать |

### Вердикт

**Используем**, потому что жизненный цикл теста — критическая часть бизнес-логики. Ошибка в статусах приведёт к тому, что студенты смогут проходить неопубликованные тесты или модерация станет бессмысленной.

## 3. OBSERVER (Наблюдатель)

### Что делает этот паттерн

**Observer** создаёт механизм подписки на события. Один объект (Subject) публикует событие, а несколько других объектов (Observers) реагируют на него, не зная друг о друге.

```python
# Без Observer (плохо)
def complete_test(student_id, test_id):
    save_attempt(...)
    update_rating(...)      # Прямой вызов
    check_achievements(...) # Прямой вызов
    send_notification(...)  # Прямой вызов
    # Добавили новую функцию? Надо менять этот метод

# С Observer (хорошо)
def complete_test(student_id, test_id):
    save_attempt(...)
    event_bus.publish("TEST_COMPLETED", {student_id, test_id})
    # Всё! Остальное сделают подписчики
```

### Где применяется в SkillFlow

**Событие:** `TestCompletedEvent`

| Подписчик | Действие |
|-----------|----------|
| `RatingUpdateHandler` | Обновляет рейтинг студента по предмету |
| `AchievementHandler` | Проверяет условия достижений, выдаёт бейджи |
| `NotificationHandler` | Отправляет уведомление в Telegram |

```
┌─────────────────────────────────────────────────────────────────┐
│                    ПОТОК СОБЫТИЙ                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Студент проходит тест                                          │
│         │                                                       │
│         ▼                                                       │
│  TestCompletedEvent (публикация)                               │
│         │                                                       │
│    ┌────┼────┐                                                  │
│    ▼    ▼    ▼                                                  │
│ Rating  Achievement  Notification                              │
│ Handler   Handler      Handler                                  │
│    │        │            │                                      │
│    ▼        ▼            ▼                                      │
│  БД       БД          Telegram                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Почему именно этот паттерн

| Критерий | Объяснение |
|----------|------------|
| **Слабая связанность** | Модуль тестов не знает про модуль рейтингов |
| **Расширяемость** | Чтобы добавить новое действие на завершение теста, просто создаёте нового подписчика |
| **Тестируемость** | Каждый обработчик тестируется отдельно |
| **Производительность** | Обработчики можно выполнять асинхронно |

### Почему не альтернативы

| Альтернатива | Почему отказались |
|--------------|-------------------|
| **Прямые вызовы функций** | Каждый новый обработчик требует изменения существующего кода (нарушение Open/Closed Principle) |
| **Очередь задач (Celery)** | Избыточно для учебного проекта, требует отдельной инфраструктуры |
| **Webhooks** | Слишком сложно для внутреннего взаимодействия модулей |

### Вердикт

**Используем**, потому что геймификация требует реакции на множество событий. Без Observer код завершения теста разрастётся до 50+ строк с вызовами всех возможных действий.

## 4. STRATEGY (Стратегия)

### Что делает этот паттерн

**Strategy** позволяет выбирать алгоритм выполнения задачи во время выполнения программы. Разные стратегии реализуют один интерфейс, но работают по-разному.

```python
# Без Strategy (плохо)
def calculate_rating(score, mode):
    if mode == "standard":
        return score
    elif mode == "tournament":
        return score * 2
    elif mode == "bonus":
        return score + 100
    # Новый режим? Меняем эту функцию

# С Strategy (хорошо)
class RatingStrategy(ABC):
    def calculate(self, score: int) -> int:
        pass

class StandardStrategy(RatingStrategy):
    def calculate(self, score: int) -> int:
        return score

class TournamentStrategy(RatingStrategy):
    def calculate(self, score: int) -> int:
        return score * 2

# Использование
strategy = TournamentStrategy()
rating = strategy.calculate(score)
```

### Где применяется в SkillFlow

| Стратегия | Когда используется | Формула |
|-----------|-------------------|---------|
| `StandardStrategy` | Обычное прохождение теста | `баллы × 1` |
| `BonusStrategy` | Тесты со сложностью 5 | `баллы × 1.5` |
| `TournamentStrategy` | Турнирные тесты (Фаза 2) | `баллы × 2 + бонус за место` |
| `FirstTryStrategy` | Первая попытка без ошибок | `баллы + 50` |

### Почему именно этот паттерн

| Критерий | Объяснение |
|----------|------------|
| **Гибкость правил** | Можно менять систему начисления баллов без изменения кода тестов |
| **Тестируемость** | Каждая стратегия тестируется отдельно |
| **Конфигурируемость** | Стратегию можно выбирать через настройки (БД или конфиг) |
| **Масштабируемость** | Новые правила добавляются новым классом, без изменения старых |

### Почему не альтернативы

| Альтернатива | Почему отказались |
|--------------|-------------------|
| **Одна функция с if-else** | Нарушает Open/Closed Principle, каждый новый режим требует изменения кода |
| **Хардкод формулы в сервисе** | Невозможно изменить правила без передеплоя |
| **Формула в БД** | Сложно валидировать, отлаживать и тестировать |

### Вердикт

**Используем**, потому что система геймификации должна быть гибкой. Преподаватели могут захотеть изменить правила начисления баллов для разных дисциплин — Strategy позволяет это сделать без переписывания кода.

## 5. FACTORY METHOD (Фабричный Метод)

### Что делает этот паттерн

**Factory Method** предоставляет интерфейс для создания объектов, но позволяет подклассам или методам решать, какой класс instantiate. Клиент не знает конкретный класс создаваемого объекта.

```python
# Без Factory (плохо)
if question_type == "single":
    question = SingleChoiceQuestion(text, options)
elif question_type == "multiple":
    question = MultipleChoiceQuestion(text, options)
elif question_type == "text":
    question = TextQuestion(text, answer)
# Новый тип? Меняем этот код везде

# С Factory (хорошо)
class QuestionFactory:
    @staticmethod
    def create(question_type: str,  dict) -> Question:
        if question_type == "single":
            return SingleChoiceQuestion(**data)
        elif question_type == "text":
            return TextQuestion(**data)
        # Новый тип? Добавляем один метод в Factory
```

### Где применяется в SkillFlow

**Создание вопросов разных типов:**

| Тип вопроса | Класс | Данные |
|-------------|-------|--------|
| `SINGLE_CHOICE` | `SingleChoiceQuestion` | Текст + список вариантов + 1 правильный |
| `MULTIPLE_CHOICE` | `MultipleChoiceQuestion` | Текст + список вариантов + несколько правильных |
| `TEXT_ANSWER` | `TextQuestion` | Текст + правильный ответ (строка) |
| `MATCHING` (Фаза 2) | `MatchingQuestion` | Текст + пары для соответствия |

### Почему именно этот паттерн

| Критерий | Объяснение |
|----------|------------|
| **Инкапсуляция создания** | Логика создания вопросов в одном месте |
| **Расширяемость** | Новый тип вопроса = новый класс + одно изменение в Factory |
| **Валидация** | Factory может проверять корректность данных перед созданием |
| **Чистый код** | Контроллеры не содержат условий `if type == ...` |

### Почему не альтернативы

| Альтернатива | Почему отказались |
|--------------|-------------------|
| **Конструктор с параметром типа** | Требует проверки типа в каждом месте создания, дублирование кода |
| **Отдельные функции для каждого типа** | Нет единой точки создания, сложно отслеживать все типы |
| **Прямое создание классов в контроллере** | Контроллер знает слишком много о структуре вопросов |

### Вердикт

**Используем**, потому что система тестов должна легко расширяться новыми типами вопросов. Factory централизует логику создания и валидации.

## 6. ADAPTER (Адаптер)

### Что делает этот паттерн

**Adapter** преобразует интерфейс одного класса в интерфейс, ожидаемый клиентом. Позволяет объектам с несовместимыми интерфейсами работать вместе.

```python
# Без Adapter (плохо)
# Код бота напрямую зависит от API бэкенда
async def handle_test_command(message):
    response = await http.get("http://backend:8000/api/tests")
    data = response.json()
    # Парсинг ответа прямо в хендлере

# С Adapter (хорошо)
class TelegramAdapter:
    def get_tests(self, chat_id: str) -> List[Test]:
        response = self.api_client.get("/tests")
        return self._parse_tests(response)
    
    def send_test_list(self, chat_id: str, tests: List[Test]):
        keyboard = self._build_keyboard(tests)
        self.bot.send_message(chat_id, "Тесты:", reply_markup=keyboard)
```

### Где применяется в SkillFlow

| Адаптер | Что адаптирует | Для кого |
|---------|---------------|----------|
| `TelegramAdapter` | Telegram Bot API → Внутренние команды системы | Telegram-бот |
| `EmailAdapter` (Фаза 2) | SMTP API → Внутренние уведомления | Система уведомлений |
| `MoodleAdapter` (Фаза 2) | Moodle API → Внутренние данные | Интеграция с LMS |

**Пример работы TelegramAdapter:**
```
Сообщение бота → Adapter → Команда API → Backend
"Пройти тест"      → parse() → POST /attempts → Обработка
```

### Почему именно этот паттерн

| Критерий | Объяснение |
|----------|------------|
| **Изоляция изменений** | Если Telegram изменит API, меняется только Adapter |
| **Тестируемость** | Можно мокать Adapter без реального бота |
| **Переиспользование** | Один Adapter может использоваться в нескольких хендлерах |
| **Чистая логика** | Бизнес-логика бота не содержит вызовов Telegram API |

### Почему не альтернативы

| Альтернатива | Почему отказались |
|--------------|-------------------|
| **Прямые вызовы Telegram API в хендлерах** | Код бота становится зависим от библиотеки aiogram, сложно тестировать |
| **Общая библиотека для всех интеграций** | Telegram и Email слишком разные, нужен отдельный адаптер для каждого |
| **Отсутствие абстракции** | Любое изменение API бота потребует переписывания всей логики бота |

### Вердикт

**Используем**, потому что Telegram-бот — это внешний клиент с собственным API. Adapter изолирует эту зависимость и позволяет тестировать логику бота без реального соединения с Telegram.

---


| Паттерн | Проблема которую решает | Альтернатива | Почему лучше |
|---------|------------------------|--------------|--------------|
| **Repository** | SQL-запросы разбросаны по коду | Active Record | Изоляция БД, тестируемость |
| **State Machine** | Некорректные переходы статусов | Поле status в БД | Валидация на уровне кода |
| **Observer** | Сильная связанность модулей | Прямые вызовы | Расширяемость без изменений |
| **Strategy** | Жёстко закодированные правила | if-else в функции | Гибкое изменение алгоритмов |
| **Factory Method** | Дублирование логики создания | Конструктор с типом | Единая точка создания |
| **Adapter** | Зависимость от внешнего API | Прямые вызовы API | Изоляция внешних зависимостей |
