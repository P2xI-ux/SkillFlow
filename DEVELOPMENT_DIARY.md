## Требования для перехода от MVP к полноценному проекту начального уровня

Ниже зафиксированы обязательные требования, выполнение которых переводит SkillFlow из состояния MVP в состояние устойчивого проектного решения начального уровня.

### 1) Функциональная полнота (обязательно)
- Полный рабочий сценарий для студента: регистрация → создание теста → отправка на модерацию → публикация преподавателем → прохождение теста → результат → рейтинг → достижения.
- Полный рабочий сценарий для преподавателя: регистрация → закрепление предметов → очередь модерации по своим предметам → approve/reject с комментарием → просмотр аналитики.
- Telegram-сценарии должны быть согласованы с web API: link-code, просмотр тестов, открытие теста, отправка попытки, получение статистики и рейтинга.
- Все 4 типа вопросов должны корректно работать end-to-end: SINGLE_CHOICE, MULTIPLE_CHOICE, TEXT_ANSWER, MATCHING.

### 2) Формальные бизнес-правила (обязательно)
- Проходить тесты может только студент.
- Проходить можно только опубликованные тесты.
- Повторная попытка возможна только при явном подтверждении (`allow_retake`).
- Модерация доступна только преподавателю и только по закреплённым дисциплинам.
- Тест создаётся в статусе DRAFT и меняет состояние только через допустимые переходы state machine.
- Рейтинг считается по предметам, а повторная попытка корректирует рейтинг через дельту.
- Достижение не может выдаваться повторно одному и тому же пользователю.
- Telegram link code имеет TTL и инвалидируется после использования/истечения.

### 3) Архитектурная дисциплина (обязательно)
- Слои должны быть разделены: API → Services → Repositories → Models.
- Вся бизнес-логика находится в service-слое, а не в роутерах и не в Telegram-боте.
- Репозитории не содержат бизнес-правил, только доступ к данным.
- EventBus используется как механизм расширения (новые реакции добавляются подписчиками без изменения core-flow).
- Реализация паттернов должна быть не только «декларативной», но и реально использоваться в рабочих сценариях:
  - Repository
  - State Machine
  - Observer/EventBus
  - Strategy
  - Factory
  - Builder
  - Visitor
  - Adapter
  - Dependency Injection

### 4) Целостность данных и транзакционность (обязательно)
- Все критические операции (создание теста, прохождение теста, модерация, пересчёт рейтинга, выдача достижений) выполняются в управляемых транзакционных границах.
- При любой ошибке система делает rollback без «полусохранённых» сущностей.
- Уникальные ограничения в БД должны гарантировать:
  - уникальность email,
  - уникальность telegram_id,
  - уникальность пары student-subject в rating,
  - уникальность пары student-achievement.

### 5) Валидация и безопасность (обязательно)
- Входная валидация должна ловить неконсистентные payload до сервисного слоя.
- Валидация профиля должна проверять связки институт/кафедра/направление по каталогу.
- Пароли хранятся только в виде хэша.
- Доступ к защищённым методам — только по JWT и RBAC-проверкам.
- Для Telegram-интеграции должен быть явный trust boundary (бот не получает прямого доступа к БД).

### 6) Тестирование как критерий готовности (обязательно)
- Unit-тесты: state machine, scoring visitor, strategy selection, achievement rules, catalog validation.
- Integration/API-тесты: auth, create/submit/moderate/attempt flows, ratings, stats, telegram connect.
- Регрессионные тесты на ретейк, дельту рейтинга, ивенты TEST_COMPLETED/TEST_PUBLISHED.
- Минимальный порог: тесты должны запускаться в CI и быть зелёными в чистом окружении.

### 7) Эксплуатационная готовность (минимальный production-ready уровень)
- Обязательный CI pipeline: install → lint → test → build.
- Структурированные логи по ключевым событиям (user_id, test_id, event_name, status).
- Прозрачный процесс миграций (Alembic) без ручных «магических» изменений схемы.
- Документированный процесс запуска (локально и Docker Compose) и healthcheck.

### 8) Нефункциональные критерии для «проекта, а не MVP»
- Предсказуемое поведение под умеренной нагрузкой (без деградации рейтингов и модерации на десятках/сотнях пользователей).
- Отсутствие критических runtime-ошибок в основных сценариях.
- Единые контракты API для web и Telegram каналов.
- Повторяемая сборка и запуск новой среды без ручных исправлений кода.

## Definition of Done (готовность начального проектного уровня)
SkillFlow считается не MVP, а проектом начального уровня только если одновременно выполнено:
1. Все обязательные бизнес-сценарии работают end-to-end.
2. Все ключевые бизнес-правила подтверждены автотестами.
3. Архитектурные паттерны реально задействованы в production flow.
4. Данные защищены транзакциями и БД-ограничениями.
5. Безопасность (hash/JWT/RBAC/TTL) реализована и протестирована.
6. CI стабильно запускает тесты в чистом окружении.
7. Документация и запуск воспроизводимы для новой команды без «устных договорённостей».
